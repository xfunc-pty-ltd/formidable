# Acceptance benchmark

Every row below is a workaround pattern that shows up when you wire FluentValidation into
Blazor's `EditForm` without a library like this one — the kind of integration code a form-heavy
codebase tends to accumulate one footgun at a time. Each pattern maps to a Formidable mechanism
that answers it natively, and each row cites where that answer is actually exercised in this
repo: a sample page you can run, a test that pins the behavior, or both. Nothing below is
attributed to a specific other library — these are patterns anyone hand-rolling the same
integration is likely to reach for, not a critique of any one project's choices.

Rows are omitted rather than padded: a pattern with no shipped sample or test demonstrating its
answer isn't listed here yet.

| Workaround pattern | Formidable mechanism | Proof |
|---|---|---|
| A hand-written orchestration/manager class sitting between the form and the validator, owning lifecycle state no single component owns | The engine lives inside the root component (`FormidableForm`/`FormidableValidator`) — there's no separate manager to construct, inject, or keep in sync | [`/`](../samples/Formidable.Sample/Pages/Quickstart.razor) · `tests/Formidable.Blazor.Tests/FormidableFormComponentTests.cs` |
| A supplementary message store layered on top of the library's own, plus a dedup pass to stop the same issue appearing twice across the two stores | One single-writer `ValidationMessageStore` — nothing to deduplicate because there's only one store | `tests/Formidable.Blazor.Tests/FormValidationEngineServerIssueTests.cs` (`Applying_the_same_server_payload_twice_does_not_duplicate`, `Same_field_issues_replace_across_calls`) |
| Submit-only completeness rules that never render inline because the integration only ever runs one, default rule set | Validation profiles are first-class; the submit pipeline always runs the submit profile, so submit-only rules are just rules in that profile | [`/profiles`](../samples/Formidable.Sample/Pages/Profiles.razor) · `tests/Formidable.Tests/DraftSubmitValidatorTests.cs` (`Submit_profile_adds_submit_rules`) |
| A hand-rolled reflection helper resolving FluentValidation's string error paths against the live object graph | `IModelIntrospector` — one cached, tested path resolver shipped in the core package | `tests/Formidable.Tests/ReflectionModelIntrospectorTests.cs` |
| A per-form strategy class hard-coding which fields' errors are currently allowed to be visible, mirroring the markup's conditional rendering by hand | Render-registration disclosure — a field's visibility is a side effect of whether something registered it while mounted, so there's no separate strategy to write or keep in sync with the markup | [`/disclosure`](../samples/Formidable.Sample/Pages/Disclosure.razor) · `tests/Formidable.Blazor.Tests/FieldRegistryTests.cs` |
| Submit-time error tracking keyed by positional path string, so deleting or reordering collection rows can misattribute an error to the wrong row | The submit-visible set is keyed by object instance, not index or path string — reordering or deleting rows can't relocate an error | [`/collections`](../samples/Formidable.Sample/Pages/Collections.razor) · `tests/Formidable.Blazor.Tests/FormValidationEngineSubmitTests.cs` (`Row_identity_survives_reorder`) |
| Custom render-dispatch / `SynchronizationContext` plumbing to make sure a debounced or async validation result actually triggers a render | The root component's own `InvokeAsync` marshals every validation-triggered update — no dispatcher delegate to write or probe for | [`/async`](../samples/Formidable.Sample/Pages/AsyncRules.razor) · `tests/Formidable.Blazor.Tests/FormidableFormComponentTests.cs` |
| A scoped/injected manager whose lifetime outlives one form, needing an explicit "begin a new session" reset call between forms | Engine lifetime equals component lifetime — construction and `Dispose()` are the whole story, nothing to reset by hand | `tests/Formidable.Blazor.Tests/FormValidationEngineLiveTests.cs` (`Dispose_detaches_from_edit_context`) |
| A `RuleSets` (or similar) parameter on the validator-attachment component that has to be kept consistent with whatever the live/typing-time validation pass runs, or the two start fighting each other | Live and submit validation run separate profiles by construction (`LiveProfile` / `SubmitProfile`) — there's no shared rule-set parameter for the two to disagree about | `tests/Formidable.Blazor.Tests/FormValidationEngineLiveTests.cs` (`Field_change_applies_live_profile_issues_for_that_field_only`) |
| A parameter threaded through wrapper component after wrapper component so a nested selection control's validation message can find the right field identifier | `FormidableField`/`ValidatedInputBase` resolve and register their own field — there's no identifier to thread through anything wrapping them | [`/foreign`](../samples/Formidable.Sample/Pages/ForeignControl.razor) · `tests/Formidable.Blazor.Tests/FormidableFieldTests.cs` (`Field_registers_for_disclosure`) |
| Manually creating, and re-creating, the `EditContext` whenever the bound model instance is swapped (draft load, reset) | `FormidableForm` owns the `EditContext`; swapping the `Model` parameter rebuilds it and resets validation state automatically | `tests/Formidable.Blazor.Tests/FormidableFormComponentTests.cs` (`Model_swap_rebuilds_edit_context_and_resets_state`) |
| Bespoke wiring to make sure a model's "clear the fields that don't apply anymore" cleanup step actually runs before every save and is re-enforced server-side | `INormalizableModel.Normalize()` — one hook, enforced at the server boundary before validation by both adapters; call it yourself on the client before a lenient draft save if you want pre-submit normalized data | [`/server`](../samples/Formidable.Sample/Pages/ServerRoundTrip.razor) · `tests/Formidable.AspNetCore.Tests/EndpointFilterTests.cs` (`Normalize_runs_before_validation_and_the_handler`), `tests/Formidable.AspNetCore.Tests/ValidateAttributeTests.cs` (`Normalize_runs_for_mvc_arguments_too`) |
| Hand-assembling a distinct, human-readable field list for an error dialog or summary, separately from whatever the inline messages already computed | `SubmitOutcome.VisibleErrorSummary` — distinct display names for the currently-visible errors, ready for a dialog or summary | `tests/Formidable.Blazor.Tests/FormValidationEngineSubmitTests.cs` (`Submit_shows_only_revealed_fields_and_reports_their_display_names`) |
| A CSS-class extension method reimplemented per project to decide a field's invalid/valid styling from its validation state | `FormidableCss.Compute` plus the `FieldCssClassProvider` bridge — one rule, shared by every Formidable input and by plain `InputBase` descendants alike | `tests/Formidable.Blazor.Tests/FormidableFieldTests.cs` (`Css_rule_matrix`, `Native_input_base_gets_provider_class_names`) |
| A bespoke component for rendering a collection-level rule's message (e.g. "at least one row is required"), separate from the per-field message component | `<CollectionMessage For="...">` — registers the collection's own path for disclosure and renders its issues, same rendering as a field message | [`/collections`](../samples/Formidable.Sample/Pages/Collections.razor) · `tests/Formidable.Blazor.Tests/FieldMessageTests.cs` (`Collection_message_registers_and_shows_collection_level_errors`) |
| A server-rejected save landing in a generic error dialog because there's no path from the response body back to the specific fields that failed | The server-error round trip: deserialize the response, flatten it with `ToIssues()`, and hand it to `Engine.ApplyServerIssues(...)` — the exact fields the server rejected light up inline | [`/server`](../samples/Formidable.Sample/Pages/ServerRoundTrip.razor) · `tests/Formidable.Blazor.Tests/FormValidationEngineServerIssueTests.cs` (`Server_issues_land_inline_on_unregistered_fields_too`) |
| A submit handler that can be bypassed — a toolbar button, keyboard shortcut, or second call site that runs the validator directly instead of routing through the same gate the form's own submit uses, so two code paths can disagree about whether submission may proceed | `FormidableForm.SubmitAsync()` is the one submit pipeline: it's both the handler wired to the rendered `EditForm`'s `OnSubmit` and a public method any other trigger can call directly — there's only ever one gate to go through | [`/`](../samples/Formidable.Sample/Pages/Quickstart.razor) · `tests/Formidable.Blazor.Tests/FormidableFormComponentTests.cs` |
| A hand-rolled base validator class with an enum or string flag selecting which rule subset to run, reinvented per project because FluentValidation itself has no first-class notion of "which lifecycle stage is this" | `DraftSubmitValidator<T>` ships that base class once, over `ProfiledValidator<T>`, with `ValidationProfile` as the selector — nothing to reinvent per project | [`/profiles`](../samples/Formidable.Sample/Pages/Profiles.razor) · `tests/Formidable.Tests/DraftSubmitValidatorTests.cs` (`Submit_profile_adds_submit_rules`) |
