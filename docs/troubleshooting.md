# Troubleshooting

These symptoms run build-time to run-time, top to bottom. Each row names what you saw, why it
happens, and the fix.

| Symptom | Why | Fix |
|---|---|---|
| A new project won't build: `RZ9991` on every `@bind-Value` — `The attribute names could not be inferred from bind attribute 'bind-Value'` — plus a run of `RZ10012` warnings about unresolved component names. | The kit isn't in scope, so the Razor compiler reads `<FormidableInputText>` as plain markup and the `@bind-Value` on it as an attribute nothing can bind. The error describes binding syntax and never mentions the namespace; the diagnostic that does name it is `RZ10012`, which is a warning, and warnings are what a reader scrolls past to reach the errors. | Add `@using Formidable.Blazor` to `_Imports.razor`, and `using FluentValidation;` plus `using Formidable.Blazor;` to `Program.cs`. [Quickstart](quickstart.md). |
| A page won't build: `CS0103` — `The name 'context' does not exist in the current context`, or that sentence naming whatever a `Context="…"` called it — on a line inside a `<FormidableForm>`, with `RZ10012` warnings elsewhere in the same build. Or: the project builds clean and the page's own labels and headings appear while every Formidable component renders nothing. | The same missing namespace as the row above, on a page with no `@bind-Value` to turn it into a Razor error. An unresolved `<FormidableForm>` is plain markup: it declares no `context` for its body to read, so the C# error lands on the line reading it. Where nothing reads one, `RZ10012` is the only diagnostic, and a warning does not fail the build unless the project promotes warnings to errors. The elements then ship as markup the browser treats as unknown: their children render, the components produce nothing. | Add `@using Formidable.Blazor` to `_Imports.razor`, as above. And read the build's warnings, not only its errors: `RZ10012` says `Found markup element with unexpected name 'FormidableForm'. If this is intended to be a component, add a @using directive for its namespace.` It names the fix that the C# error cannot. [Quickstart](quickstart.md). |
| A page won't build: `RZ9999` — `The child content element 'ChildContent' of component 'FormidableField' uses the same parameter name ('context') as enclosing child content element 'ChildContent' of component 'FormidableForm'`, with the same wording for a `Virtualize` inside a form, or a `FormidableValidator` inside an `EditForm`. | Both components take a typed `ChildContent`, and an unnamed typed fragment claims the implicit `context`. Nesting one inside another puts two claims on that one name. What collides is the declaration, not any use of it, so the diagnostic arrives whether or not either body ever reads `context`. `EditForm` has always charged the same rename. | Name either fragment: `Context="field"` on a `FormidableField`, `Context="gadget"` on a `Virtualize`, `Context="formidable"` on a `FormidableValidator` inside a consumer's own `EditForm`, or on the `FormidableForm` itself, which names the outer body and leaves the inner one on `context`. [`/async`](../samples/Formidable.Sample/Pages/AsyncRules.razor) is the one sample naming the outer body; every other page that owes the rename puts it on the inner fragment. [Component kit](component-kit.md#formidableformtmodel). |
| Submit answers with an HTTP 400: `The POST request does not specify which form is being submitted. To fix this, ensure <form> elements have a @formname attribute with any unique value, or pass a FormName parameter if using <EditForm>.` | The browser posted the form itself, so no Blazor component saw the submit. Two shapes arrive there: a page that is statically server-rendered with no interactivity coming, or a `<form>` the page owns rather than `FormidableForm` (attach mode's `EditForm`, or any form the page writes) submitted inside the prerender window, before the circuit or the WebAssembly runtime had started. `FormidableForm`'s own `<form>` renders `inert` for that window, so a visitor cannot operate one there. The message's advice cannot be followed on the first path anyway: `FormidableForm` has no `FormName` parameter to pass. | Give a page that has no render mode one: `@rendermode InteractiveServer`, `@rendermode InteractiveWebAssembly` or `@rendermode InteractiveAuto`. `FormidableForm` refuses to render where the renderer reports itself static with no interactivity coming, asking for a render mode in its own words; this 400 is what a host whose renderer says nothing answers instead. For a form the page owns on a page that already has a render mode, put the window out of reach the way `FormidableForm` does (`inert="@(!RendererInfo.IsInteractive)"` on the `<form>`), or take the window away with `@rendermode @(new InteractiveServerRenderMode(prerender: false))`. [Hosting models](hosting-models.md#what-happens-inside-the-prerender-window). |
| Every request fails with `InvalidOperationException`: `Validate<Order>() found no endpoint argument of that type`. Or `[Validate]` runs the action on a payload it should have rejected. | `Validate<TModel>()` needs a handler parameter of that type, and refuses a handler without one when the endpoint's pipeline is built. Routing builds every endpoint before it matches a request, so one mis-wired endpoint fails every request until it is fixed. `[Validate]` with no type named on it validates the arguments whose type has a registered validator and skips an argument MVC bound to `null`; with `RequireValidator` off (the default) an action that hands it nothing is not an error. | Declare the model as a parameter of the handler (a group's `Validate<TModel>()` needs it on every handler in the group). On MVC, register the validator and set `RequireValidator = true`, so an action that could never hand the filter a model throws instead of validating nothing. [What stops them from validating at all](server-integration.md#what-stops-them-from-validating-at-all). |
| Messages appear, but no field turns red or green. | Formidable ships no CSS. What a field gets is a class name: `formidable-invalid` while it has an error, and `formidable-valid` once it is touched or modified, has no issue to show and a submit would pass it. The colour is your stylesheet's. | Add rules for `formidable-invalid` and `formidable-valid` to your stylesheet ([tutorial stage 2](tutorial/2-draft-and-submit.md#see-the-state) has a starter one), or map the five names onto a UI library's own with `FormidableOptions.CssClasses`. [CSS and accessibility](css-and-accessibility.md#need-to-know), [`CssClasses`](options.md#cssclasses). |
| A field says nothing until Submit is pressed. | Either you have not changed the field's value yet, or the form's `LiveProfile` leaves that rule to Submit. A message shows as you edit only for a field whose value you changed and committed, and tabbing through a field is not a change. Why: [how the engine works: the live view](how-the-engine-works.md#the-live-view). | Type into the field and commit the change (blur, under the default `UpdateOn`) and the message answers from there on, until the field leaves the rendered page. If the form sets `LiveProfile`, the narrowing is the cause: unset it to have the live channel follow the submit profile, or give the one rule membership in the narrow profile as well. [Validate while typing, on blur, or only at submit](recipes.md#i-want-to-validate-while-typing-on-blur-or-only-at-submit), [presence rules wait for submit](recipes.md#i-want-presence-rules-to-wait-for-submit-while-formats-answer-live), [narrow what the live channel validates](recipes.md#i-want-to-narrow-what-the-live-channel-validates). |
| A field never turns green before Submit, or `IsFormValid` stays `false`. | Green means a submit would pass the field, so it waits until every rule the submit profile selects has answered for the value as it stands. Where `LiveProfile` is narrowed, or the validator is one the engine cannot take rule by rule, that answer comes only from a check that answers the whole form (a submit, the whole-form re-check, a load of values, or `TrackFormValidity`'s validity check). `IsFormValid` reads `false` until `TrackFormValidity` is on. Why: [Async validation](async-validation.md#why-isnt-my-field-green-even-though-the-check-passed). | Set `TrackFormValidity = true`: its validity check answers the rest, and feeds the `Valid` class and `IsFormValid` alike. On a validator the engine can take rule by rule, unsetting `LiveProfile` lets the edit's own check answer the submit rules. [What puts green on a field](css-and-accessibility.md#what-puts-green-on-a-field), [`TrackFormValidity`](options.md#trackformvalidity). |
| A warning or info message shows, but the field wears no state class. | `formidable-invalid` paints the moment the field has an error to show, whatever the visitor has done. The warning, info and valid classes wait until the field is touched or modified, while every message surface shows whatever the form holds for the field. | Nothing to fix: a committed change to the field brings the class with it. To colour the message itself, style `formidable-message--warning` and `formidable-message--info`. [Why does a field show a message but no state class](disclosure.md#why-does-a-field-show-a-message-but-no-state-class). |
| Clicking a summary entry does nothing. | Click-to-focus looks the field up by its deterministic id and reports whether that element took focus. Either no rendered element carries the id (a control the page renders itself, or a field with no input of its own), or one does and will not take focus, which is what a container without `tabindex`, a disabled control, or a collapsed section around the field each produce. | Render the id and make the element focusable: `id="@field.ElementId"` on an input, or `FormidableFieldId.For(field)` plus `tabindex="-1"` on a container. Where the field cannot be made reachable up front, wire a `FocusFallback` to reach it on the retry. [Every summary entry lands somewhere](recipes.md#i-want-every-summary-entry-to-land-somewhere). |
| A blocked submit moves focus nowhere. | Focus aims at the element carrying the first error's id. It misses where nothing renders that id, or where the element that does will not take focus (disabled, inside a closed `<details>`, a container without `tabindex`), and a miss with no `FocusFallback` wired is logged as `did not take focus`. No move is asked for at all under `FocusFirstErrorOnInvalidSubmit="false"`, after `SuppressFirstErrorFocus()` in the `OnInvalidSubmit` handler, or from an attach-mode page that submits through `Engine` rather than the validator's `ValidateForSubmitAsync()`. | Render the id on an element that takes focus (`id="@field.ElementId"` on an input; `FormidableFieldId.For(field)` with `tabindex="-1"` on a container), wire `FocusFallback` for a field that cannot be reached up front, and in attach mode submit through `ValidateForSubmitAsync()`. [Why did nothing take focus](css-and-accessibility.md#why-did-nothing-take-focus). |
| A hand-wired control never validates live, even though it picks up the state classes. | Its handler calls `MarkTouched()`, which marks the field touched without telling the form its value changed. A field the form was never told about never joins the live channel, so no message shows for it as you edit, while a touched field with no issue of any severity is styled valid as soon as the form knows a submit would pass it. Why: [how the engine works: what green reads](how-the-engine-works.md#the-submit-coverage-vouch). | Call `field.NotifyChanged()` from the change handler. `MarkTouched()` belongs on blur, where there is no new value to judge. [Use a native or third-party control](recipes.md#i-want-to-use-a-native-or-third-party-control). |
| My code changed a value, or a button of mine changed a list, and no message answered. | The form hears a change only as a field-changed notification, and a write to a model property or an edit to a list sends none. The change starts no check, no message answers it as you edit, and the field is judged as it was until something else makes the form look again. | Call `field.NotifyChanged()` (or `EditContext.NotifyFieldChanged(...)`) after the write; for a list, call it on the context of the `FormidableField` wrapping the collection; for a model filled all at once, call `DiscloseLoadedValuesAsync()`. [Why did a value my code changed keep its old message](async-validation.md#why-did-a-value-my-code-changed-keep-its-old-message), [what happens when a row leaves or the list reorders](collections-and-row-identity.md#what-happens-when-a-row-leaves-or-the-list-reorders). |
| The `aria-invalid` I wrote on a native `InputText` disappears. | A Blazor `InputText` answers `aria-invalid` from the field's messages each time its parameters are set or validation state changes. With no messages it removes the attribute it holds, and the page's own value returns only when the page around the input renders again. A debounced or async check landing, the whole-form re-check after a submit, and a server reply applied in the background each change validation state with no render of the page in between. | Answer the attribute from `GetFieldState(field).HasErrors` (the same `true`-or-nothing the framework writes) and subscribe to `Engine.StateChanged` to re-render on it, as `/vanilla` and `/workout` do; or leave the attribute to the framework. [Why did my own `aria-invalid` vanish from a native `InputText`](css-and-accessibility.md#why-did-my-own-aria-invalid-vanish-from-a-native-inputtext). |
| axe reports an `aria-describedby` naming an id nothing on the page carries. | A kit input names its messages id while the field has issues, and `FormidableForm` names the model-level one on its `<form>` always. The id exists only where the matching message component is placed, and a reference to nothing is permitted and ignored, so nothing misbehaves. | Place the component the attribute names: `FormidableFieldMessage` (or `FormidableCollectionMessage`) for the field, `FormidableModelMessage` for the form. [Why does axe flag an `aria-describedby` that points at nothing](css-and-accessibility.md#why-does-axe-flag-an-aria-describedby-that-points-at-nothing). |
| Required markers and `aria-required` vanished, and a loaded draft stopped confirming the values its rules pass, after the form was given its own `Validator`. | The validator passed in is used whole. A wrapper that implements only `IModelValidator<TModel>` cannot report what its rules require of a field, and the form treats it exactly as it treats a validator whose rules cannot be read at all: no marker beyond what `RequiredOverride` declares, and a loaded draft that discloses its wrong values but confirms none of its good ones. Why: [how the engine works: what a validator can be asked](how-the-engine-works.md#rule-level-versus-whole-profile-execution). | Derive the wrapper from `DelegatingModelValidator<TModel>`, which forwards all three interfaces and answers each tester with the wrapped validator's own answer. [Wrap the validator without losing what it can do](recipes.md#i-want-to-wrap-the-validator-without-losing-what-it-can-do). |
| A date input reports impossible years while it is being typed. | A native date input fires `change` once per segment, so validating on every change judges half-typed values. | Set `UpdateOn="InputUpdateMode.OnBlur"` so the rules run once you leave the field, with the value settled. [Validate while typing, on blur, or only at submit](recipes.md#i-want-to-validate-while-typing-on-blur-or-only-at-submit). |
| A message sits on the wrong row after a remove or reorder. | Rows rendered without `@key` are reused by position, so the components that registered one row now display another's value while their messages, id and aria attributes stay with the row that moved away. Nothing on screen says so, and by default nothing throws. | Key each row by the row object (`@key="row"` on the element the loop renders), never by an id whose object can be replaced, with `For` and `@bind-Value` closing over that row. Turn on `VerifyRowKeys` in Development so a misfiling throws with the fix in its message. [Why did my message move rows](collections-and-row-identity.md#why-did-my-message-move-rows). |
| A rule on the list itself (`NotEmpty()` on a `List<T>`) shows its message nowhere. | A list property has no input to register it, and a submit shows a message only for a field something on the page has registered. A `FormidableFieldMessage` on the list registers nothing, so at a submit it has no message to render. The failure still blocks, and when it is the only one the form explains itself with its model-level sentence instead. | Render `<FormidableCollectionMessage For="() => Model.Items" />` for each collection carrying a rule of its own: it registers the field and lists its messages in one component. [Where does a collection-level rule's message go](collections-and-row-identity.md#where-does-a-collection-level-rules-message-go). |
| `VerifyRowKeys` threw from my own notify after my code replaced a nested object. | A fresh instance is a fresh field, and the components bound to the old one keep speaking for it until the page renders again. A notification sent before that render re-renders them in the middle of the call: each now names the replacement while its registration names the instance that left. With the check off they go on answering for that instance. | Render first (`row.Child = selected; await InvokeAsync(StateHasChanged);`), then notify with `EditContext.NotifyFieldChanged(...)` built from the accessor, not `NotifyChanged()` on a context captured before the swap. [What happens when my code replaces the object a field is bound to](collections-and-row-identity.md#what-happens-when-my-code-replaces-the-object-a-field-is-bound-to). |
| Two inputs render the same `id`, so a summary click or `aria-describedby` reaches the wrong one. | An id is derived from the owning object and the field name. Two roots over one model instance (two `FormidableForm`s, or a `FormidableForm` beside a `FormidableValidator`) compute identical ids for every field both render, and among thousands of row objects rendered at once two can draw the same owner segment. Validation is untouched either way. | Bind each root to its own model instance; virtualize a list that large so only the rows in view render. [Can two fields end up with the same id](css-and-accessibility.md#can-two-fields-end-up-with-the-same-id). |
| The server's error never appears, though client errors do. | The page posts from `OnValidSubmit`, so a rule only the server owns cannot speak until every client rule passes. | Expected ordering: clear the client errors and the server's verdict arrives last. Post without that gate if the server should answer first. [Validate on the server and show its verdict](recipes.md#i-want-to-validate-on-the-server-and-show-its-verdict). |
| The server's errors land inline but its advisories show nowhere. | A server error blocks the save, so it shows whether or not its field is on screen. A server advisory blocks nothing, so it follows the client's own rule and shows only where something renders its field. Why: [Disclosure](disclosure.md#why-did-a-server-error-show-on-a-hidden-field). | Render the field (or a `FormidableFieldAnchor` for one the page draws itself); the browser console names each dropped advisory with `Formidable: issue at '...' is suppressed`. [Validate on the server and show its verdict](recipes.md#i-want-to-validate-on-the-server-and-show-its-verdict). |
| A server error stays after I fix the field. | A message a server reply put on screen stands until the whole form is re-checked: `RefreshDebounce` (300 ms) after your next committed edit or a change to which fields are on screen, at the next submit, or when the page calls `DiscloseLoadedValuesAsync()`. The edit's own check leaves it standing, and a client rule failing the same way keeps its own message throughout. | Expected: the re-check replaces it a moment after the edit commits, as the next submit does. `RefreshDebounce = Timeout.InfiniteTimeSpan` turns the re-check off, and the server's answer then stands until the next submit or load of values. [What happens to a server error when I edit the field](server-integration.md#what-happens-to-a-server-error-when-i-edit-the-field). |
| Applying a server reply moved focus. | `FormidableForm.ApplyServerIssues` treats a reply carrying an error as a blocked submit that arrived late. It lands the visitor on the first error on the page (not necessarily the one just applied), under the same `FocusFirstErrorOnInvalidSubmit` switch (`true` by default); a reply with no error in it moves nothing. | Set `FocusFirstErrorOnInvalidSubmit="false"`, or apply through `Engine.ApplyServerIssues(...)`, the quiet path, and call `FocusFirstErrorAsync()` yourself when you want the move. [Why did focus move when I applied the reply](server-integration.md#why-did-focus-move-when-i-applied-the-reply). |
| Reading a 400 body throws inside my submit handler: `JsonException` behind a proxy or gateway, or `NotSupportedException` once the app is published. | `ReadFromJsonAsync` reads the body whatever `Content-Type` says, so an HTML page or plain text throws `JsonException`, a character set the runtime lacks throws `InvalidOperationException`, and the JSON literal `null` deserializes to `null`, which `ApplyServerIssues` rejects. The generic `ReadFromJsonAsync<FormidableValidationProblem>()` throws `NotSupportedException` under trimming, which a WebAssembly Release build turns on. In a Blazor handler each is an unhandled exception. | Read through `FormidableValidationProblemJsonContext.Default.FormidableValidationProblem`, which needs no reflection. Parse inside a `try` catching everything the parse can throw (`JsonException`, `InvalidOperationException`, `NotSupportedException`), treat a `null` result as no verdict, and say so in the page's own words; the last verdict stays on screen. [What if the 400 is not Formidable's](server-integration.md#what-if-the-400-is-not-formidables). |
| A warning shows twice after a server reply, once from each side. | The client's copy and the server's count as one only when the message text and the severity match exactly, so two phrasings of the same advisory both show. | Keep the two sides' message text in step (share the validator assembly and its message resources between client and server), the same way their rules are kept in step. [Why did the same warning show once when both sides sent it](server-integration.md#why-did-the-same-warning-show-once-when-both-sides-sent-it). |
| A warning is on screen but the submit succeeded. | Warnings and infos never affect validity: `CanProceed` counts error-severity issues only. | That is the severity doing its job: give error severity to the validator that must block. `.WithSeverity` attaches to the one it follows rather than to the whole rule. [Advise without blocking](recipes.md#i-want-to-advise-without-blocking). |
| A native `ValidationMessage` or `ValidationSummary` shows errors but never a warning or info. | A native component reads the messages the `EditContext` itself carries, and those are errors only, at no severity it can express, from a client rule or a server reply alike. Warnings and infos show in Formidable's own message components and in the summary. | Render `FormidableFieldMessage` (or `FormidableSummary`) beside or instead of the native component; `GetIssues` and `FieldState.HasWarnings` carry the full set for markup of your own. [Why does a native `ValidationMessage` show a server error but not its warning](server-integration.md#why-does-a-native-validationmessage-show-a-server-error-but-not-its-warning). |
| Submit is blocked but no field shows a message. | Every field that failed is hidden, and nothing on screen or in the summary discloses its error, so the form blocks and explains itself with one model-level message rather than failing silently. Edits elsewhere leave that explanation standing while nothing on screen explains the block. Why: [how the engine works: the gate](how-the-engine-works.md#the-gate-latch). | Give that explanation a surface: a `FormidableSummary` lists it among everything else, and a form built on inline messages alone renders a [`FormidableModelMessage`](component-kit.md#formidablemodelmessage), which is fixed to the model-level field the explanation belongs to. Then check the browser console for `Formidable: issue at '...' is suppressed` (or watch `SuppressedIssueDiagnostic` for the same events in code), and check whether the rule needed a mirrored `.When(...)`. [Reveal fields conditionally without losing their rules](recipes.md#i-want-to-reveal-fields-conditionally-without-losing-their-rules). |
| The summary names a field that is not on screen. | A field a submit has shown stays watched until the form passes or is reset, so hiding it afterwards takes the message off its own row without taking the entry out of the summary. A `DisclosureOverride` returning `true` also discloses fields that were never rendered. Why: [how the engine works: what a submit reveals](how-the-engine-works.md#the-reveal-ledgers). | Fix the value: the entry goes as soon as the next check that runs the submit profile finds the rule no longer producing the issue (on the defaults, the edit itself). Keep the override where it is deliberate, as virtualized rows are. [Reveal fields conditionally without losing their rules](recipes.md#i-want-to-reveal-fields-conditionally-without-losing-their-rules). |
| A message lingers after the value was fixed. | A message clears at the next check that runs its rule after a committed change, so a lingering one is waiting on that check. A change that never committed starts none (under the default `UpdateOn` the commit is the element's `change` event, which a text box fires when you leave it). A `LiveDebounce` window holds the check back until the typing quiets. A `LiveProfile` narrowed past the rule leaves the message to the whole-form re-check that follows a post-submit edit, `RefreshDebounce` (300 ms) after the value commits and after any check already running has finished. Why: [how the engine works: which check yields to which](how-the-engine-works.md#supersession-and-deferral). | Commit the change: leave the field, set `UpdateOn="InputUpdateMode.OnInput"` to commit on every keystroke, or call `field.NotifyChanged()` from a control the page wires itself. Where the debounce or the narrowing is deliberate, wait it out or tune `FormidableOptions.RefreshDebounce`. [Validate while typing, on blur, or only at submit](recipes.md#i-want-to-validate-while-typing-on-blur-or-only-at-submit), [async check with a pending indicator](recipes.md#i-want-an-async-check-with-a-pending-indicator). |
| After a submit, my rule runs twice for one edit. | On a validator the engine can take rule by rule (FluentValidation's `AbstractValidator<T>` with its class-level cascade left at `Continue`), one edit runs each rule once, whichever check reaches it first. A class-level `CascadeMode.Stop`, or a validator that is not an `AbstractValidator<T>`, has every rule run on every check. A rule reached through `Include()` may run again where `LiveProfile` differs from the submit profile, pressing Submit asks every rule again, and `TrackFormValidity` can ask an async rule again. | Leave `ClassLevelCascadeMode` at `Continue` (a per-rule `.Cascade(CascadeMode.Stop)` changes nothing), and memoize an async rule that Submit or `TrackFormValidity` asks again. [Does the library ever run my rule twice for one edit](async-validation.md#does-the-library-ever-run-my-rule-twice-for-one-edit). |
| The same value is checked again after being typed, cleared and typed back. | Every committed change gets a fresh answer, however familiar the value, and pressing Submit asks the rule again. A memo answers a repeat from what it already knows, for a window you size. | Hold an `AsyncRuleMemo<TKey, bool>` as a field on the validator and write the rule with `MustAsyncMemoized` where `MustAsync` would go ([remember a slow check's answer](recipes.md#i-want-a-slow-async-check-to-remember-its-answer)). [Why did the same value get checked twice, and how do I stop it](async-validation.md#why-did-the-same-value-get-checked-twice-and-how-do-i-stop-it). |
